# 后段控制结果仍可能被旧前段future挡住

2026-10-27。本目录只做本机CPU分析，没有访问服务器、占卡、启停服务或修改框架源码。

结论：**KNOWN_LIMITATION_CONFIRMED**。当前StageRPCBridge虽然能把动作限定给一个PP阶段，但它仍沿用原全局FutureWrapper的读取顺序，因此不是独立的阶段控制通路。这个结论不代表新设计验收通过。

## 一个CPU例子说明限制

固定一条调用顺序：先提交“第二个批次的前段计算”，再提交“第一个批次的后段释放条件检查”。

| 顺序 | CPU案例里发生的事 | 说明 |
|---|---|---|
| 1 | 后提交的后段控制回复已经准备好 | 本例预先备好全部16份CPU回复载荷，刻意排除worker回复缺失 |
| 2 | 核心尝试读取这个后段控制结果 | 直接调用真实StageRPCBridge.collect |
| 3 | 真实FutureWrapper先去读取更早的前段回复，进入等待 | 后段控制回复尚未被读取，虽然其载荷已经准备好 |
| 4 | CPU测试主动放行旧前段的等待条件 | 这是测试清理，不是实际KV恢复或HCCL完成 |
| 5 | 旧前段回复返回后，后段控制回复才被读取 | 线程正常退出，没有留下挂起任务 |

本例只证明**后提交的结果会先触发对旧future的等待**。它没有使用真实MQ、设备或KV；旧前段由CPU Event暂时挡住，后段回复由标准库小对象提供。没有测量或报告模型性能耗时。

如果某种实际调度流程必须先由核心处理后段控制结果，才能使旧前段继续，那么把该控制结果排在旧前段的全局future后面，就有循环依赖风险。**本例没有证明真实框架已经出现这条循环，更没有证明HCCL死锁。** 是否构成真实死锁还取决于实际发送、接收、派发顺序和设备进度。

## 具体代码依据

归档文件：

- 原75—85行：新future通过`futures_queue.appendleft(self)`加入同一队列。
- 原87—96行：无论调用哪个future的`result()`，都先`pop()`队列尾部较旧的future，再执行它的`_wait_for_response()`。
- 原98—106行：真正取得回复发生在`self.get_response()`，不是回复载荷准备好时自动完成。

当前原型`../executor_bridge.py`的92—117行：`collect()`直接调用`future.result()`，没有绕过上述顺序。它还要求`seen == all_workers`，即使本次只有一个阶段处理动作，仍核对全部16个worker的回复；这属于另一个需要设计的范围约束。本CPU例子已提供全部16份回复，所以没有把这项约束混入测试结果。

精确源码路径和AST行号保存在`验证结果.json`。

## 对修改方案意味着什么

1. 阶段就绪、释放和接收控制结果需要能在旧模型结果尚未完成时被核心处理；不能只换一层StageCommand，却继续等待同一个全局future队列。
2. 阶段回复范围要覆盖该阶段真正必要的TP worker确认，避免无关阶段的空回复成为门槛；也不能随便只取一个rank，就省略其他必要确认。
3. 必须区分RPC身份、worker身份和返回类型，并明确每个回复队列由谁读取。不能简单再开一个线程抢读原MQ，造成旧回复被当作新控制回复。
4. 阶段控制结果提前处理，不等于整个模型批提前完成。最终token、采样、请求进度、KV所有权及整批提交仍保留原有顺序和资源约束。

本目录没有实现上述修改。完整核心接入、新消息协议、真实NPU正确性和性能收益仍是NOT_VERIFIED。

## 它要缩短哪一段等待

原异步规则下：前段KV已经恢复，但整请求恢复确认尚未齐，不能开始前41层计算。新规则希望让这部分计算与后段KV的剩余恢复重叠。后段仍要等自己的KV和前段中间结果两项都齐，才能执行后37层。

这与“提前下发整批，然后worker自己等KV”的同步候选不同。也不能把历史218—240ms全部算作本设计能省下的时间：真实通知何时到达核心、前段是否有空位、两段KV恢复相差多大，都影响最终收益。

## 为什么CPU验证值得先做

这轮在上卡前已经发现并处理了几类问题：

1. 后段forward完成后若立即派下一批，原runner尚未交接采样状态，会拒绝下一次execute。现在末段名额保留到真实最终结果可用。
2. 先等后段接收返回，再派前段，会出现“后段等前段元数据、前段还没派发”的互等。现在先把接收和前段计算都非阻塞排入，再等结果。
3. 同一阶段的某个worker先做接收后处理，可能卡在TP all-gather。现在先收齐整段通信完成确认，再共同后处理。
4. 控制器用“批次ID＋代次”，worker最初却用字符串；单独测试没发现，组合前已统一为tuple。
5. 正常的“发送尚未结束”不能用异常当轮询结果，否则真实RPC会按worker失败处理。现在先以不释放资源的探测确认可释放，再执行释放。

这些检查证明控制规则与实际方法能按预期衔接，**不证明提速**。

## 这版在什么条件下才可能提速

- **前段先恢复、后段仍在恢复**：有机会把前41层的计算插进等待后段KV的时间里。可重叠的上限受两段恢复完成的时间差和前段计算长度共同限制，不是等多久就能省多久。
- **后段早已恢复、前段最后恢复**：单靠“分段就绪”通常没有恢复时序上的计算重叠可争取。若真正拖延的是完成消息晚到核心，就要解决独立通知消费；不能拿分段原型通过替代这项修改。
- **名额或缓冲已经满**：即使前段KV就绪，也仍然不能继续派发。不能为了展示更早派发就提前释放还在使用的整批名额。

目前还没有本设计在真实业务中的收益数据。历史通知等待既不能直接全部算作可节省时间，也不能当作PP2相对PP1新增的耗时。

后续CPU检查进一步确认：当前桥接仍沿用全局FutureWrapper读取顺序，已准备好的后段控制回复也可能先等待旧前段future。真实源码抽取与有限时间案例见`integration_gaps/README.md`，状态为KNOWN_LIMITATION_CONFIRMED；这不是新设计验收通过，也没有证明真实HCCL死锁。阶段控制的独立消费和回复路由仍属于必须补齐的真实接入工作。

## 中午如果只有一台16卡，能验什么

原P的TP8/PP2本身已使用16卡；原D的DP4/TP4/PP1还需要另一台16卡机器。只有单机时可以验证P侧的阶段协议与设备依赖，不能复现原两机1P1D的端到端对照。

如果两侧资源齐备，先检查阶段事件顺序、模型和传输正确性，再按已确认的客户数据口径比较原异步ON与候选ON。正式请求规模和资源窗口须以用户新确认为准，不把旧窗口当作授权。本轮不重跑已有OFF。

性能判定必须同时看：真实KV完成→核心处理、前段派发／设备执行、后段输入到达／派发、最终首token四处时刻。前段较早启动但最终首token没提前，只能说阶段依赖改变，不能说TTFT改善。TPOT、吞吐和失败数也需要检查，避免只优化首token却拖慢整体。

# 前段先就绪为何还不等于实际派发

当前完整P候选两次hot只观测到后段先ready，约26.4/27.7ms后前段ready；4行trace均为阶段恢复登记，没有batch admission/execute/worker设备完成。原组与候选第二hot约658/653ms，不能据此证明新阶段路径或收益。本说明只读当前本机源码，不改生产代码、不新增人工延迟实验；先继续既定自然冷/热PD。

因此，“frontfirst时一定马上触发”不成立。设计保证的是：**core获得正常重新schedule机会时，若所有门成立且legacy全局完成尚未抢先消费，可partial预约；实际组批带tag后再由driver派发。** 短暂front-only窗口可能在core再次组批前消失；legacy全局完成也会合法回旧路径。当前新增`partial_admission_decision`能区分这些门，但旧完整P进程没有热加载该新增日志，不能拿其缺失反推具体哪一门失败。

## N16正常producer的边界

N16当前是Mooncake＋LMCache的正常P producer，不是standalone local-first-token。它不会因为没有local-first-token标记而被上述helper硬跳过；MTP3配置本身也不被helper禁止。但若实际请求已带draft/placeholder或剩余计算量不为1，会被请求scope拒绝。是否实际加载candidate和4个flags、真实请求字段是否合规，须由本轮进程来源/日志确认，不能从准备文件推定。

已有CPU证据为reservation 8/8、TP8/TP4的Scheduler→wire→真实AsyncScheduler组合2/2及wire 9项，模型/设备/通信/KV manager仍有fixture。它们没有验收N16正常producer的Mooncake＋LMCache双Connector、远端消费、MTP及异步保存/释放整生命周期。不能把“无producer静态拒绝”写成“正常PD已可安全提前执行”，也不能把已修好的draft构造问题与阶段派发混为一项验收。

## 自然机会出现时应看到什么

同一request/generation/batch至少须串起：

1. `stage_kv_ready_observed`前段门先满足，all=false。
2. `partial_admission_decision`为reserved/front_ready，request_global_finished=false；随后`stage_batch_admitted`（driver228行）带真实batch。
3. `stage_execute_submitted stage=0`（driver260行）仅说明CPU提交；须继续看到所有前段TP的`worker_stage_execute_begin`及`worker_model_device_complete_observed`（worker1182/1201行）。
4. 后段真实KV门满足及同批activation完成后，出现`all_kv_ready_back_dispatch_eligible`（driver342行）、后段提交/worker开始/设备完成。
5. 真实sample解析与全rank输出、`core_fifo_model_output_consumed`（driver407行），并核对请求/保存/远端消费的正常结束与回收。

前段worker开始是必要的host执行证据，仍不等于kernel已开始。要证明设备计算与真实back恢复重叠，需NPU trace，或“前段设备已完成而back仍未真实提交/真实Future仍未完成”的同窗事实；不能只比较CPU提交或被延后投递的host通知。当前完整P两hot不具备这条证据链。

## 人工延迟方案仅保留设计边界，当前不执行

在back worker的`start_load/submit`里同步sleep不是有效捷径：它可能卡住旧零tokenRPC，core即使登记front ready，也要等原Future返回才有新schedule机会，反而制造不出admission窗口。若未来确需实际back恢复延迟，必须非阻塞推迟真实提交、保留原request/generation/producer event/块引用，让零tokenRPC仍能正常返回；还需单独审查提交线程设备context、真实Future接管和异常保留，不能直接加Timer线程便称可用。

更低侵入的“真实完成后暂缓back CPU proxy与独立通知共同发布”只能验证host admission/wire；仅延迟独立通知而让legacy完成先可见，仍可能回原路径。该方法不制造成功、不改数据，但back数据已实际恢复，不能证明计算与真实restore重叠，也不能用于性能比较。**本轮不新增这两类人工延迟实验或其他测试组合。**
